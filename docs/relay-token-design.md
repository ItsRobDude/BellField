# BellField Relay Token Design

This document pins the Phase 5 prerequisite: the per-shop relay credential
primitive from [delivery-relay-plan.md](./delivery-relay-plan.md) §3 and build
order step 1. The relay consumes this primitive; it does not invent it.

It complements [license-design.md](./license-design.md): the signed license
file is the offline right-to-run proof; the relay token is the revocable
online credential. They are issued together and never merged.

## Goals

- One opaque, revocable credential per shop granting exactly "use the relay
  as this shop, within entitlement."
- Single-active enforcement: two live servers must not silently share one
  shop's identity.
- Legitimate server replacement (death, migration, restore drill) works
  without a support ticket.
- Revocation is one BellField-side step and touches nothing on customer
  hardware.
- A stolen backup set must not contain a usable relay credential.

## Non-Goals

- No provider credentials in the token, ever (custody rule, relay plan §1).
- No account-level authority: the token cannot manage billing, domains, or
  other shops.
- No offline verification: the relay is online by definition, so the token
  carries no signature scheme to validate locally.
- No expiry date: lifecycle is revoke/reissue, not time-based rotation.
- Not a licensing mechanism: a revoked token stops relay-backed features
  only; the software keeps running.

## Token Format

The token is an opaque bearer secret:

```text
bfrt1_<tokenId>_<secret>
```

- `bfrt1` — format version prefix; future formats bump the digit.
- `tokenId` — short random identifier (16 hex chars) used for relay-side
  lookup; not secret on its own.
- `secret` — 32 random bytes, base64url without padding.

Rules:

- The relay stores only `tokenId` plus a SHA-256 hash of the full token
  string. The plaintext token exists exactly once, in the issuance output.
- Comparison is constant-time against the stored hash.
- Deliberately not a JWT: server-side lookup gives instant revocation, and
  there is no offline-verification requirement to justify signed structure.

## Wire Protocol

Every install→relay call carries:

```text
Authorization: Bearer bfrt1_...
X-BellField-Server-Instance: <serverInstanceId>
```

Auth outcomes:

- `401` — unknown, malformed, or revoked token. Non-retryable on the install
  side: queued sends fail with the structured non-retryable code, not an
  endless retry loop.
- `403` — shop suspended (abuse/flap review, relay plan §8). Non-retryable.
- Network errors and `5xx` — retryable; the install queues per the Phase 5.3
  semantics.
- Quota exhaustion is **not** an auth failure: it is reported by the
  entitlement endpoint and the send response (relay plan §5) so the office
  gets the decided sending-limit copy.

## Single-Active Activation

Each installed server has a `serverInstanceId`: a random UUID generated by
`write-server-config.mjs` into `bellfield-server.env` alongside the other
generated secrets.

Properties that placement buys:

- The env file is excluded from backup sets, so neither the relay token nor
  the instance id rides along with a backup. A restore onto the **same**
  machine keeps the same env file and the same identity — no rebind, no
  friction.
- A **replacement** machine gets a fresh env (the operator reruns
  `write-server-config.mjs`), hence a fresh instance id.

Binding rules (v1, decided):

1. On first authenticated call, the relay binds the token to the presented
   instance id.
2. A call presenting the same token with a **different** instance id rebinds
   automatically — activation moves to the new server, and the relay records
   the rebind event. This is what makes server death, migration, and
   replacement zero-ticket.
3. **Flap detection** is the enforcement: rebinds are expected to be rare
   (an event per machine change). Two live servers sharing a token rebind on
   nearly every call. When rebinds exceed the relay's flap threshold inside
   the detection window, the relay flags the shop for review and may suspend
   it (`403`). Threshold and window are relay operational config, tuned in
   Phase 5.1 — the mechanism, not the numbers, is what this design pins.

Rationale: hard "first binding wins, support must release" was considered and
rejected for v1 — it converts every legitimate replacement into a support
ticket while a cloned install with a copied env defeats it anyway. Automatic
takeover plus flap detection makes dual-running loud instead of silent, which
is the actual requirement (relay plan §3), and makes credential theft visible:
the legitimate server starts failing instead of silently coexisting.

Suspension surfaces office-side as the standard generic delivery-unavailable
copy. Per the no-internal-leakage rule, tokens, bindings, and instance ids
never appear in office UI; the System surface may show a neutral delivery
service state (connected / not configured / unavailable).

## Issuance and Lifecycle

Issuance is BellField-side relay tooling (lives with `apps/relay`, never in
the release artifact):

- `create shop` — relay DB row: shop id, display name, `licenseId` from the
  issued license file (reconciliation bookkeeping only; the relay never
  verifies license signatures).
- `issue token` — generates the token, stores the hash, prints the plaintext
  **once**. At most one active token per shop: issuing atomically revokes any
  prior token.
- `revoke token` — one step; effective on the next request.
- `inspect` — shop status, token status, current binding, recent rebinds,
  last-seen timestamp, for support diagnostics.

Compromise response is reissue + update the shop server's env file. No grace
overlap in v1: the old token dies when the new one is born, and the minutes of
relay-feature downtime during the swap are covered by the install-side queue.

Delivery of the plaintext token to the customer uses the same trusted channel
as the license file during install/support — never email through the relay
itself.

## Install-Side Configuration

Unified server config (`bellfield-server.env`, already ACL-restricted to
Administrators + LocalSystem):

```text
BELLFIELD_RELAY_BASE_URL=https://relay.bellfield.app
BELLFIELD_RELAY_TOKEN=bfrt1_...
BELLFIELD_RELAY_SERVER_INSTANCE_ID=<generated uuid>
```

Rules:

- never stored in the install's database, the license file, or backup sets
- absent config means relay-backed features report not-configured through the
  existing readiness path (`EstimateEmailDeliveryStatus`); nothing else
  degrades
- `BELLFIELD_ESTIMATE_EMAIL_RESEND_API_KEY` is deleted when the adapter swap
  lands (execution plan 5.2); it must never coexist with relay config on a
  sold install

## Relay-Side Storage (informative)

Pinned loosely; exact migrations are Phase 5.1 implementation detail:

- `shops` — id, display name, `license_id`, status (`active | suspended`)
- `relay_tokens` — id (`tokenId`), shop id, token hash, status
  (`active | revoked`), created/revoked timestamps
- binding state per token — bound instance id, bound-at, last-seen
- `token_events` — append-only: issued, revoked, bound, rebound, suspended;
  this is the flap-detection input and the support audit trail

## What Depends On This

- Execution plan 5.1 (relay service v1) implements auth, binding, and the
  issuance CLI exactly as pinned here.
- Execution plan 5.2 (install adapter swap) consumes the env config and maps
  `401/403` to non-retryable failure codes.
- License issuance flow (Phase 3 tooling) is unchanged; the only coupling is
  copying `licenseId` into the shop record at issuance time.
